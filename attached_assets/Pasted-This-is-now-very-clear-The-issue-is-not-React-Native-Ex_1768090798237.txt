## The most common root causes (in your case)

### 1. You are using a **user-level token**, not a **business-scoped token**

For example:

* Token was created at signup
* Token was created before the business existed
* Token is missing `business_id` in its claims

Backend expects:

```json
{
  "sub": "user_123",
  "business_id": "bd4275c3-7261-4e85-aed1-fca1c0d88e0f"
}
```

But token actually has:

```json
{
  "sub": "user_123",
  "business_id": null
}
```

or a different ID.

---

### 2. Business was created, but token was never refreshed

Very common in SaaS flows.

Flow looks like this:

1. User signs up → token issued
2. User creates business → business ID generated
3. Token is **not reissued**
4. User calls `/workflows/init` → backend rejects

---

### 3. Expo Go masking the real auth lifecycle

This line is important:

```
Expo Go app detected. Using RevenueCat in Browser Mode.
```

Expo Go:

* Does not run native auth persistence properly
* Can reuse stale tokens
* Does not simulate production session refresh

This **does not cause the 403**, but it makes it easier to hit.

## How to fix this properly (not a workaround)

### ✅ Fix #1: Ensure the token is business-scoped

When you create or select a business, you **must reissue the token**.

Backend example:

```ts

→ returns NEW JWT with business_id claim
```

Frontend:

```ts

await setAuthToken(newToken);
```

Do **not** reuse the signup token.

Frontend should never guess business IDs.
